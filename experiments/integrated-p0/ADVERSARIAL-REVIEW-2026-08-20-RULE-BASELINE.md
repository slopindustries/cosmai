## F2 — a record whose rule never ran is reported `clean` (Major)

**Claimed.** `run()`'s docstring: *"'checked and clean' and 'checked and wrong' are both

dropped and never guessed."*

**Why false.** Abstention is implemented at *item* granularity only. At *rule* granularity
the add-on abstains silently and then reports the record as clean.

**Reproduction.** Drive `run()` with a trend point identical to the test fixture but with

`[측정]` `test_period_outside_window_does_not_fire_when_the_window_cannot_be_parsed`

## F3 — the determinism proof does not cover the determinism claim (Major)

**Claimed.** AC2: *"Determinism is proved, not claimed: the same snapshot at the same add-on
version produces byte-identical `body` values across two runs."* DP-019 D4 is what that
serves, and `canonical_body`'s own docstring frames it as "byte-identical" across runs.

**Why the proof is thinner than the claim.** Two structural facts, both measured:

1. `[확인 사실]` `domain.store.canonical_body` serialises with `sort_keys=True`. So key
   ordering in the emitted `body` **cannot** affect the digest. Asserting digest equality
   proves nothing about key order — that half of the claim is carried by the canonicaliser,
   not by the add-on.
2. `[측정]` Both `run()` calls in `TestItIsDeterministic` happen **in one process**, so any
   output derived from a hash-randomised iteration order is identical between them and
   differs between runs of the repository.

**Reproduction (M35).** Change one `expected` string from a tuple join to a set join —
the smallest realistic mistake for this exact code, since `TREND_MARKER_KEYS` and
`BLOG_MARKER_KEYS` in the same file *are* `frozenset`s:

```python
f"one of {', '.join(set(TREND_DIMENSIONS))}"     # was: ', '.join(TREND_DIMENSIONS)
```

Then digest one `dimension: "shopping_device"` trend point per seed:

```
PYTHONHASHSEED=0  3613833525b92e57…      PYTHONHASHSEED=3  3fc6f48aaaa92f81…
PYTHONHASHSEED=1  3613833525b92e57…      PYTHONHASHSEED=4  2afa77c29809e7e7…
PYTHONHASHSEED=2  3fc6f48aaaa92f81…      PYTHONHASHSEED=5  9a9f49e42ccd8ed0…
```

Four distinct digests. And:

```
pytest -k ItIsDeterministic → 2 passed, 55 deselected
```

`[측정]` **The shipped add-on is genuinely seed-stable** — restored, seeds 0–3 all give
`9a9f49e42ccd8ed0…`. So this is a control gap, not a defect: the code is right and the test
would not have told anyone if it were not. `[추론]` The fix is one line — take the second
digest from a subprocess, or parametrise the existing test over two `PYTHONHASHSEED` values.

The different-input control (`test_a_different_input_produces_a_different_digest`) is real
and does its job; it is the *positive* control that is missing, not the negative one.

## F9 — `streams = []` is indistinguishable from omitting `[declares]` (Minor)

**The worker's question, answered.** `[확인 사실]` `Declarations.from_toml`'s inner
`string_list` does `data.get(key, [])` and returns `tuple(raw)`. So a missing key and `[]`
both produce `()`. `_check_kind_consistency` then tests `if manifest.declares.streams:`,
which is `False` for both. **Empty and omitted are byte-identical to the loader** — measured
above as `streams=()`, the same value `normalizer.conformance` gets from having no
`[declares]` block at all.

`[측정]` The manifest comment therefore overstates: *"`[declares]` is empty, and that is not
an omission"* asserts a distinction no mechanism makes. It is a comment-only signal.

`[측정]` `normalizer.naver.blog/addon.toml:31-32` already carried the same `[declares]
streams = []`, so this is a copied precedent rather than a new invention, and
`test_addon_api_contract.py:216` does test that a normalizer declaring `streams = ["items"]`
is refused. What no test covers is this add-on's own `declares.streams == ()` —
`TestTheManifest` checks `hosts`, `endpoints`, and `needs_credential` and stops.

## F11 — the finding echoes untrusted input verbatim (Moderate)

`[측정]` `_finding`'s `found` copies the offending value straight from the parsed payload,
with no bound and no serialisation check.

- **Size.** A trend point whose `ratio` is `{"nested": "A"*200000}` fires
  `trend.ratio_invalid` and produces a **200 175-byte** `canonical_body` from a 200 179-byte
  input. `body` is persisted as `Jsonb(dict(result.body))` (`domain/store.py:record_results`),
  so the result table inherits the input's size.
- **Non-strict JSON.** `json.loads` accepts `NaN`/`Infinity` by default, and both collectors
  serialise raw payloads with `json.dumps` defaults, which emit them. A `ratio: NaN` reaches
  `found: NaN`, and `canonical_body` emits the literal:

```
b'{"clean":false,"findings":[{"expected":"between 0 and 100 inclusive …","field":"ratio","found":NaN,…'
```

  `[측정]` that byte string is not strict JSON. `[추론]` `Jsonb(dict(body))` would hand the
  same literal to PostgreSQL, which rejects `NaN` in `json`/`jsonb`, failing the whole
  `record_results` transaction — **unverified against the live cluster**, since I am scoped
  away from the database.

`[확인 사실]` `normalizer.naver.trend` already copies `ratio` through verbatim, so the `NaN`
exposure is not introduced here. What is new is that rule-baseline extends verbatim echo to
*every* field it judges, which is the widest such surface in the repository.
